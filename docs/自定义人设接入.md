# 自定义人设接入

给人设加一条来源有三条路，按「要不要写代码」从轻到重排。三条路的产物是同一个东西：
**角色库**（`<数据根>/data/persona-characters/<id>.json`）里的一条角色记录；之后在设置页
「桌宠 → 角色」里选中它、点「应用到此宠物」，那一只的 `whisperPrompt` 就被写成该角色的正文。

> 口径：**宠物引用角色**（`pets[].personaCharacter` 存角色 id），不是「来源覆盖宠物」。
> 多只宠物各引各的角色、互不影响；新增来源只影响「能扫到什么角色」，不影响已有引用。

---

## 路一：把卡片放进约定目录

不写代码，放文件即可。

```
$DSH_HOME/<项目>/persona.json          ← 单卡项目（dsh-fish-soul 的形态，已实证）
$DSH_HOME/<项目>/personas/*.json       ← 多角色项目：一个文件一个角色
$DSH_HOME/<项目>/personas/*.png        ← 同上，PNG 卡（tEXt 的 chara 块）
```

内置来源（设置页下拉里直接出现）：

| 来源 id           | 约定目录                                                                                     | 说明                                  |
| ----------------- | -------------------------------------------------------------------------------------------- | ------------------------------------- |
| `fish-soul`       | `$DSH_HOME/fish-soul/`                                                                       | 已实证的单卡形态                      |
| `dsh-soul`        | `$DSH_HOME/dsh-soul/`                                                                        | 目录约定未实证，`probe()` 决定灰/亮   |
| `dsh-rofm`        | `$DSH_HOME/dsh-rofm/`                                                                        | 同上                                  |
| `dsh-suzu-memory` | `$DSH_HOME/dsh-suzu-memory/`                                                                 | 同上                                  |
| `custom`          | 无（用 `POST /persona/scan` 的 `path` 指定；**必须是绝对路径且落在数据根或 `DSH_HOME` 内**） | 恒在列表里；不给路径时置灰            |
| `editor`          | 无                                                                                           | 「不用角色、正文自己写」，没有 `scan` |

卡片格式：SillyTavern v2（`{ "spec": "chara_card_v2", "data": { … } }`）。投影规则只有一份
（`dsh-pet/src/host/persona-source/card-reader.ts` 的 `projectCard`）：8 个字段按
人设 / 性格 / 背景 / 开场白 / 对话示例 / system / 收尾指令的顺序拼成正文，`{{char}}` 换成角色名、
`{{user}}` 换成「主人」。

扫描规则（`dsh-pet/src/host/persona-source/card-file.ts`）：先读 `persona.json`，再列
`personas/` 一层；同一份正文（按正文指纹）只留第一个，其余进 `skipped/empty`；单文件超过 1 MiB
进 `skipped/too-large`，不读。

## 路二：放文档（设置页「导入文档」）

适合「手上只有一份设定文档」的情况。入口在「桌宠 → 角色 → 导入文档…」，也可以直接调
`POST /persona/import`（细节见 [`../API.md`](../API.md) 的「人设来源与角色库」一节）。

**支持的后缀与上限**

| 类型          | 判定              | 抽取方式                                                                               | 失败原因                                          |
| ------------- | ----------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `md` / `txt`  | 扩展名            | UTF-8 解码、去 BOM、折叠 3+ 连续空行                                                   | 空文本 → `extract-failed`                         |
| `json`        | 扩展名            | 是 `chara_card_v2` → 直接取 8 字段（**跳过模型调用**）；否则按纯文本喂模型             | 坏 JSON 按纯文本兜底；仍无内容 → `extract-failed` |
| `png`         | 8 字节 PNG 签名   | 只认 `tEXt` 的 `chara` 块（SillyTavern 卡）；命中同样跳过模型                          | 无 `chara` 块 → `unsupported`（**不做 OCR**）     |
| `docx`        | 扩展名 + ZIP 魔数 | 先读中央目录做闸门（≤512 条目、解压后 ≤8 MiB），再用 `mammoth.extractRawText` 取纯文本 | 超限 / 目录损坏 / 解析失败 → `extract-failed`     |
| `.doc` 及其它 | 其余              | —                                                                                      | `unsupported`：「另存为 .docx 或直接粘贴文本」    |

- **上限**：单文件解码后 ≤ 768 KiB、合计 ≤ 768 KiB − 4 KiB（4 KiB 是 base64 与 JSON 包装的预留，保证请求体 < 1 MiB）、最多 5 个；请求体超 1 MiB 回 `413`，解码后超上限回 `200 + payload-too-large`。
- **流程**：预览（名字 / 描述 / 性格三格可编辑）→ 点「导入角色库」才落库（`POST /persona/characters/import`）。
- **预览零写盘**：抽不出来时给可读原因，磁盘一个字节都不动。

## 路三：写 `scan()`（实现接口）

适用于「角色来自数据库 / 网络 / 别的插件」的情况。注册走
`ctx.petApi7340.persona.register(source)`，最小实现如下（可直接照抄）：

```ts
// 第三方插件的最小实现（注册在 apply 里，随 ctx.effect 反注册）
const unregister = ctx.petApi7340.persona.register({
  id: "my-persona",
  name: "我的角色库",
  kind: "custom", // 'soul-card' | 'custom' | 'editor'，缺省 soul-card
  // 可用性探测：只读盘、不抛；抛了会被注册表收敛成「未安装」
  async probe(options) {
    return { installed: true, path: "/path/to/wherever" };
  },
  // 扫描：返回的 text 必须**已经是可进 whisperPrompt 的投影正文**
  async scan(options) {
    return {
      characters: [
        { name: "鱼生", text: "人设：一只蓝色大肥鱼。", path: "/db/123" },
      ],
      skipped: [],
    };
  },
  // 老协议：仍要提供（设置页与历史调用方会用它读单卡）
  async resolve() {
    return { ok: false, reason: "not-found" };
  },
  syncable: true,
});
ctx.effect(() => () => unregister(), "my-plugin: persona source");
```

**三条硬约束**

1. **只读盘、不抛**：`scan()` 里的异常等于「整个扫描失败」；单个文件坏了请放进 `skipped`
   （`reason` 用 `invalid-card` / `empty` / `too-large`），不要中断其余角色。
2. **给了 `options.path` 就只扫它**：文件 = 1 个角色，目录 = 按自己的约定扫一层；不要悄悄回落到约定目录
   （否则用户在设置页指路之后仍会看到旧结果）。
3. **单文件按 1 MiB 截断**：超过就放进 `skipped/too-large`，不要把整份内容读进内存再失败。

**没有 `scan` 的来源不会出现在「扫描并导入」里**——这是「选中即导入」的前提；`editor` 就是这种
（它表示「不用角色、正文自己写」）。

**语义补充**：`text` 是投影后的正文（不是原始字段），宿主按它算指纹去重；也可以额外带上 `data`
（8 字段）——带了就用它落库，不带则走「正文进 description」的降级路径。`syncable: false` 表示这个
来源没有可扫描的产物。注册表是模块级单例：`register` 返回注销函数，插件卸载必须调用，否则重载会撞 id 重复。

> 上面这个最小实现与内置工厂 `dsh-pet/src/host/persona-source/card-file.ts` 的 `scan()` 输出同构
> （`{ characters: [{name, text, path, data?}], skipped: [{path, reason}] }`）；
> 角色库落盘位置与 `dsh-pet/src/host/persona/characters/store.ts` 一致：
> `<数据根>/data/persona-characters/<id>.json`。

## 两条边界

1. **宠物引用角色，多只各引各的**：应用只写 `id === pet` 的那一只（`whisperPrompt` + `personaCharacter`
   - 可选 `name`），其余实例原样带回。想换角色就再点一次；想解除引用就删掉该实例的
     `personaCharacter`（正文保持现值，只覆盖不清理）。
2. **pet pack 实例本轮不可应用**：文件宠物（`skin/<名>-config.json`）的实例属于那个条目
   （`entry !== 'main'`），`POST /persona/characters/apply` 回 `persona-readonly-entry`；
   设置页把「应用 / 删除」置灰，扫描、导入与浏览角色库仍然可用。扩展点已留在
   `applyCharacter` 的写回层参数上。

## 排障

- **来源置灰** → `probe()` 回了 `installed:false`，看响应里的 `expectedPath`（也可以
  `curl "…/persona/sources"` 直接看）。
- **扫到 0 个角色** → 看 `POST /persona/scan` 响应里的 `skipped[].reason`：
  `invalid-card` 卡片格式不对、`empty` 没有可用正文、`too-large` 超过 1 MiB。
- **应用了却没变化** → 确认目标是主条目的实例（`GET /persona/sources?pet=<id>` 的 `writable`）；
  文件宠物只读。再看 `chars` 是否为 0（空正文不会写盘）。

接口细节见 [`../API.md`](../API.md) 的「人设来源与角色库」一节与 [`../openapi.yaml`](../openapi.yaml)。
