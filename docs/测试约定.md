# 测试约定

这份文档解决什么问题：四层测试各自只证明一小块，但绿灯汇总起来很容易被读成「功能没问题」。真实发生的漏检有两类：一类是「输入依赖进程 cwd」，单测里那个路径不存在、看着对，宿主里同一个相对路径却命中真实文件；另一类是「文档里的数值承诺」，所有门禁都在比较代码与自己的常量，没人去比文档的数字与传输编码能不能同时成立。本文写清每层能证明什么、不能证明什么，以及两类必须补的维度。

---

## 四层：单测 / 契约 / 浏览器 E2E / 真实宿主

在 `dsh-pet/` 包目录里跑。

| 层 | 命令 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 单测 | `npm test`（`node --test "src/**/*.test.ts"`） | 纯函数与分支逻辑、错误码口径、注入替身下的控制流 | 进程 cwd、真实 `DSH_HOME`、编码后的真实字节数、跨构建行为、浏览器渲染 |
| 契约 | `npm run typecheck` / `lint` / `format:check` / `check:cycles` / `check:openapi` / `check:runtime` | 类型与风格自洽、无循环 import、接口文档与实现同形 | 行为、数值承诺可兑现、跨层语义一致 |
| 浏览器 E2E | `npm run test:ui`（`node --test scripts/tests/*.test.mjs`） | 真实 React + Chromium 下的加载、失败重试、恢复默认、保存、中英窄窗布局 | 真宿主 IPC、Electron 窗口行为、点击穿透、显示器缩放、真实数据根写入 |
| 真实宿主 | 真 DSH 实例 + 真数据根 | cwd 相关行为、跨构建写盘、编码/体积边界、桌面窗口行为 | 其他机器/其他版本的表现；且必须先做隔离（见 [`插件升级与冒烟隔离.md`](插件升级与冒烟隔离.md)） |

关于浏览器 E2E 的既有口径（细节见 [`../dsh-pet/scripts/tests/README.md`](../dsh-pet/scripts/tests/README.md)）：它用真实 React 和 Chromium 渲染设置页、拦截配置与模型接口、只访问临时本地服务，**不读取或修改用户的 DSH 配置**；`npm test` 与 `npm run test:ui` 分开运行，普通插件安装不下载浏览器。设置 `DSH_PET_UI_ARTIFACTS` 可保存布局截图。

四层的读法：**下一层不能替上一层背书。** 单测绿不代表契约成立，契约绿不代表浏览器里能点通，浏览器绿不代表真实宿主里写对了地方——后者恰恰是最常见的越界点。

## 环境相关输入必须有 cwd 维度

先给定义：行为依赖 `process.cwd()`、`DSH_HOME`、时区、locale、显示器 DPI 这类**由运行环境提供**的输入。它们不是参数，是隐式参数，因此单测天然对它们无感。

硬规则：**凡改动涉及这类输入，测试必须包含一个 cwd 维度。** 二选一，不能两个都不做：

```ts
// 方案一：把断言搬到另一个目录再跑一遍
const prev = process.cwd();
process.chdir(await mkdtemp(join(tmpdir(), "cwd-")));
try { await expectRejected(handler({ path: "relative/file.json" })); }
finally { process.chdir(prev); }

// 方案二：直接断言「相对路径必被拒」——把产品口径写成断言
assert.equal(result.code, "bad-request");
```

反面教材（真实踩过）：接口接受一个路径参数，实现用 `existsSync(path)` 直接判定。单测 cwd 是包目录，那个相对路径不存在，于是「不存在 → `not-found`」看起来完全正确；真实宿主的 cwd 是数据根，同一条相对路径恰好命中真实文件，返回 `200` 并把内容写进了角色库。**单测全绿，缺陷在真机**。

所以「只测合法绝对路径能过」等于没测：它证明的是「正常输入能工作」，而缺陷永远在「异常/相对/越界输入」那一侧。

## 路径类输入的三件套

接收路径参数时，先定义解析基准，再写代码。产品口径优先选「必须绝对」，并在错误文案里带上收到的原值与原因。

| 步骤 | 做法 | 挡什么 |
| --- | --- | --- |
| 1. 拒绝相对 | `isAbsolute(p)` 不成立 → `bad-request` | 把进程 cwd 变成隐式契约 |
| 2. 判边界 | `realpathSync(p)` 后按 `root + sep` 前缀比 | `..` 穿越、`/data2` 冒充 `/data`、符号链接越界 |
| 3. 分语义 | 根内但不存在 → `not-found` | 把「文件没了」误报成「路径非法」 |

`realpath` 必须在**判边界之前**：先判后解析，等于让符号链接绕过检查。

允许根不要宽到「整个 `DSH_HOME`」。本仓当前的残余风险就在这里：根下任意一个可读的 `persona.json` 都能被扫进角色库。要收紧应写成一条新需求，而不是在实现里偷偷改范围。

复核清单（七种输入，缺一种就等于少测一类）：相对路径、`..` 穿越、根外绝对路径、符号链接指向根外、根内存在的文件、根内不存在的文件、空字符串/缺省。同一组输入在「测试 cwd」与「宿主 cwd」下各跑一次，行为一致才算过。

## 数值承诺要算一遍

门禁只证「代码与自己的常量一致」，不证「文档里的数字与传输编码能同时成立」。这是唯一一类**必须人工算**的检查，评审清单里应固定一条：

1. 扫出所有数量承诺：`≤ N KiB / MiB`、`最多 N 个`、`N 秒超时`、`N 字节`。
2. 对每个数字同时写下三样：客户端常量（`路径:行号`）、服务端常量（`路径:行号`）、**从客户端到服务端的编码变换**（base64？URL 编码？gzip？JSON 包装？）。
3. 编码会膨胀时用命令算边界，不要心算。
4. 判定：**任何让合法输入必然失败的边界 = P1**（用户看到的是笼统 413，属于「功能在文档承诺范围内不可用」）。

复算命令与膨胀公式见 [`上传体积上限约定.md`](上传体积上限约定.md)。那里的 `node -e` 一行命令可直接粘贴，改两个常量即可复用。

配套要求：三处（客户端常量、服务端常量、文档文案）同值，且各有一条边界断言（恰好上限放行、上限 + 1 拒绝）；客户端侧断「0 请求」而不是「有报错」。

## 什么必须上真实宿主

命中下表任一条，就不能只靠 `npm test` / `npm run test:ui` 结论收尾：

| 触发条件 | 为什么本地抓不到 |
| --- | --- |
| 输入含路径参数、且实现按 cwd 解析 | 测试进程 cwd ≠ 宿主进程 cwd；合法的两种结论各自只在一边成立 |
| 改动会写配置文件、且存在旧构建仍在线 | 跨构建分歧只在真机、只在「旧实例还活着」时出现 |
| 依赖传输编码后的真实字节数（base64 + JSON） | 单测算的是解码后字节，膨胀发生在发送那一刻 |
| 数据根解析（环境变量 / 指针 / 默认） | 本地测试多用临时目录，绕过了真实解析链 |
| 桌面窗口行为（点击穿透、置顶、DPI 缩放） | 需要 Electron 运行时，浏览器 E2E 到不了 |
| 冒烟声称「零残留」 | 只有真数据根才谈得上残留，且必须两项比对（md5 + 条目数） |

上真宿主的三条纪律：**先隔离**（`DSH_PET_USER_ROOT` 指向临时目录，或先快照）、**先写清比什么**（哪两个指标、哪些不纳入）、**跑完还原并比对**——两项都回到原值才叫零残留。

最后一句取舍：真实宿主证明的是「这台机器、这个版本、这组输入」，不能外推成「所有环境都对」。所以真宿主发现的缺陷，回头要**补一条能进 `npm test` 的断言**（通常是 cwd 维度那条），否则下一轮同样的改动会再踩一次。

## 虚拟桌面 GUI 用例的输入约束

在虚拟桌面里跑 GUI 用例时，「能截图」不等于「能输入」。

- **三条硬约束**，缺一不发 `/vdesk/input`：①目标桌面名出现在 `/vdesk/desktops` 列表里；②`/vdesk/frame` 能拿到**有内容**的帧；③该条用例确实需要 OS 级输入（穿透、拖拽、原生菜单）。
- **不要探测式点击**：坐标 (1,1) 或「随便点一下」验证路由是否可用，会落到默认桌面并在真实桌面上产生副作用（真实案例：误关一个浏览器窗口）。路由可用性只靠 `GET` 与源码判定。
- **`204 + X-Black:1` 与「返回 200 但帧里只有壁纸」都不能当放行证明**：DComp 合成的窗口不进 BitBlt 帧，两个不同桌面的帧字节可能完全相同。
- 页面内的点击/输入**优先走 CDP**（`page.click` / `page.fill` 或 `Input.dispatchMouseEvent`）；虚拟桌面输入只留给必须 OS 级的验证，并在用例里写明理由。
- CDP 拖拽 ≠ OS 拖拽：视口会随窗口移动，位移可能被反复叠加。拖拽类结论必须由真人或 OS 级输入复核。

## 业务失败走 `200 + {ok:false}` 的断言口径

本仓不少路由的业务失败**不是 4xx**，而是 `200 + {ok:false, reason, message}`；`400` 只留给「请求体不是合法 JSON」。

- 断言要写：`status === 200 && body.ok === false` 且 `body.reason` 符合预期，外加「副作用不发生」（例如配置文件 `md5` 不变）。
- 文档侧要能让机器验：`openapi.yaml` 的 200 响应用 `oneOf: [成功体, $ref FailureResponse]`，不要写死 `ok: const true`。
- 按 4xx 写断言会得出「修好了」的假结论——先读契约再写断言。

## 契约门禁与变异验证

`check:openapi` 只校验文档自身合法与路由对齐，**不校验成败两态**；单测如果只是复制实现的判据（桩），也拦不住生产回归。

- 断言要打**生产入口**（真实实现 + 真实路由），不要只测桩。
- 文档断言：读 `openapi.yaml` 结构，断言 `oneOf` 里确实有失败分支。
- **变异验证**：把修好的逻辑临时改回错误版本，确认至少一条断言变红，再改回去；还原后比 `md5` 证明逐字节一致（改动未提交时**不要**用 `git checkout` 还原）。
