# 上传体积上限约定

这份文档解决什么问题：凡是「用户可以上传文件」的接口，需求与文档里一定会写下一个数量上限。写下数字很容易，写对不容易——这个数字算的是解码前还是解码后、到服务端之前被编码膨胀了几成、客户端与服务端的常量是不是真的同值。这三件事任缺一件，就会出现「文档承诺能传 1 MiB，用户在 700 多 KiB 就被 413」，而所有门禁依然是绿的。本文给出这条链路的算法、复算命令、断言写法与两条状态码的边界。

---

## 为什么不能直接照抄「≤ N MiB」

先分清三个数。它们单位不同、由不同层负责、写错的后果也不同：

| 名字 | 量的对象 | 谁在管 | 写错的后果 |
| --- | --- | --- | --- |
| 单文件解码后字节 | 原文 | 业务规则 | 抽不动、预览失败、报错原因错位 |
| 合计解码后字节 | 原文 | 文档对用户的承诺 | 承诺在边界内兑现不了（本文主角） |
| 请求体字节 | 传输编码之后 | HTTP 层 | 笼统 413，用户不知道自己哪里超了 |

「直接照抄 ≤ 1 MiB」的错法是这样的：1 MiB 本来是 HTTP 层的**请求体**上限，文档却把它当成**解码后合计**写进承诺。同一个数字出现在两处、指的是两样东西，于是「文档认为合法的输入」在服务端必然被拒。这类缺陷不会让任何一条断言变红，因为断言比较的是「代码与自己的常量」，没有任何门禁去比较「文档的数字与传输编码能否同时成立」。

判断标准只有一句：**上限必须先说明它算的是哪一层，再写数字。** 默认口径建议写成「解码后」，因为用户能感知的是文件大小，不是请求体大小。

## base64 与 JSON 包装的膨胀

上传走 multipart 之外的 JSON 通道时，文件内容要先进 base64 再进 JSON 字段，两处都会膨胀：

- **base64 是 4/3**：原文 `n` 字节 → `4 * ceil(n / 3)` 字节。这个比例是硬性的，没有压缩余地。
- **JSON 包装是常数**：字段名、引号、逗号、外层对象大约几十字节。本仓实测约 **53 B**，随字段名长度小幅浮动。

于是「解码后合计上限」与「请求体上限」之间是一条换算式，不是一个等号：

```
body(n) = 4 * ceil(n / 3) + W          # W ≈ 53
可用原文上限 = 3 * floor((CAP - 1 - W) / 4)
```

`CAP` 取 1 MiB（1,048,576 B）时，反解出来是 **786,390 B**，也就是 768 KiB 差一点点。所以「单文件 768 KiB」是「恰好顶满请求体」的口径，**合计**必须再往下让出包装余量——本仓因此取 `768 KiB − 4 KiB`。

**不要心算，用命令复算。** 把 `CAP` 与 `W` 换成你这套接口的真实值即可直接粘贴：

```bash
# 逐档看「这份原文会不会超请求体」
node -e "const cap=1048576,w=53,f=n=>({decoded:n,b64:4*Math.ceil(n/3),body:4*Math.ceil(n/3)+w,ok:4*Math.ceil(n/3)+w<cap});console.table([f(768*1024),f(764*1024),f(748*1024)])"

# 反解：体上限下最多能传多少原文
node -e "const cap=1048576,w=53;console.log('maxDecoded =',3*Math.floor((cap-1-w)/4))"
```

复算结果会给出两条可执行结论：`768 KiB` 那一档 `body` 已经超过 `cap`（`false`），`764 KiB` 才进得去（`true`）；反解上限 786,390 B 说明「768 KiB」只能当单文件口径。

**「上限 ÷ 1.34 再向下取整」的算法**（照这个顺序做，不要跳步）：

1. 拿到可用请求体预算 `CAP`（HTTP 层的真实常量，`路径:行号`）。
2. **粗算**：`floor(CAP / 1.34)`。1.34 是「4/3 膨胀 + 一点点包装」的合并近似，用来快速拿到量级。
3. **向下取整到 4 KiB 的整数倍**：`floor(粗算值 / 4096) * 4096`。得到人类可读、可写进文档的预算。
4. **精算验一遍**：`floor((CAP - 1 - W) / 4) * 3`，与第 3 步对比；两者不一致时**以精算为准**（1.34 只是近似，`W` 会随字段名长度浮动）。
5. 若文档同时承诺「合计」，从这一步的预算里再扣一次包装余量（本仓扣 4 KiB），并把扣的理由写进注释。

以 `CAP = 1 MiB` 走一遍：粗算 782,519 B → 取整到 764 KiB（782,336 B）→ 精算 786,390 B（略大，因为 1.34 保守）；单文件仍按 768 KiB 定，合计取 `768 KiB − 4 KiB`。

## 三处同值：客户端 / 服务端 / 文档

一个上限在仓库里至少活在三处，**三处必须是同一个数值表达式，不是同一个说法**：

| 处 | 本仓位置 | 值 |
| --- | --- | --- |
| 客户端（选文件时就拦） | `dsh-pet/src/client/settings/use-persona-import.ts` | `MAX_IMPORT_TOTAL_BYTES = 768 * 1024 - 4096` |
| 服务端（解码后复检） | `dsh-pet/src/host/persona-import/extract.ts` | `MAX_IMPORT_TOTAL_BYTES = 768 * 1024 - 4096` |
| 文档（用户读到的承诺） | [`自定义人设接入.md`](自定义人设接入.md) / `API.md` | 「合计 ≤ 768 KiB − 4 KiB（4 KiB 是 base64 与 JSON 包装的预留）」 |

三条硬规矩：

1. **写成算式，不要写成字面量**。`768 * 1024 - 4096` 自带推导；`782336` 三个月后没人知道它为什么是这个数。
2. **每一处都留一句为什么**：注释写「给 base64 与 JSON 包装留余量，保证请求体 < 1 MiB」。数字会被改，理由会被保留。
3. **「已同步」只能由值证明**。报告里写「三处已同步」不算，把三个文件的 `路径:行号` 与实际值并排列出来才算；本轮就出现过「只改服务端与文档、客户端仍是旧值、报告声称已同步」而被打回的情况，判定依据是三行常量，不是自述。

## 边界断言怎么写

上限类常量必须有边界断言，且**两侧都要有**：

| 断言 | 期望 | 说明 |
| --- | --- | --- |
| 恰好等于上限 | 放行 | 证明上限没被写小 |
| 上限 + 1 字节 | 拒绝，且原因可读 | 证明上限没被写大 |
| 上限 − 1 字节 | 放行 | 抓 off-by-one 的另一种方向 |

**客户端一侧要断「发出去几个请求」，不是「有没有报错」。** 客户端拦截的价值在于「注定 413 的体根本没有出门」，所以断言应该写在请求计数上：超限选择 → `0` 次上传请求 + 一条本地提示。只断「界面上出现了错误文案」会漏掉「先发出去再被拒」这种实现，用户仍然白等一个来回。

服务端一侧的断言要同时覆盖两层：解码后超限（业务码）与请求体超限（HTTP 层）。两层各一条，别合并。

## 两个 413 语义不要混

「超了」其实有两种，用户能做的事完全不同，必须靠响应体里的 `code` 分开：

| 场景 | 状态码 | 业务码 | 用户能做什么 |
| --- | --- | --- | --- |
| 请求体超过 HTTP 层上限 | `413` | `body-too-large` | 少选几个文件 / 换更小的文件；文案只能说「请求过大」 |
| 解码后超过承诺上限 | 优先 `200` + 失败结果（本仓口径），或 `413` + `payload-too-large` | `payload-too-large` | 明确指出是哪个文件、超了多少，可精确处理 |

两条纪律：

1. **HTTP 层那条不要试图解释业务**。它拿不到文件名，说多了就是假信息；它只负责「这个体我不读」。
2. **业务层这条必须可行动**：带上文件名与「解码后 X 字节 / 上限 Y 字节」。两个都回同一句「请求过大」，用户与日志都分不清是网络层还是业务层，排查会从头再来一遍。

顺带一条易混项：**「文件数上限」与「字节上限」是两个独立触发器**，错误码不同、文案不同，不要合并成一个数、一条消息。
