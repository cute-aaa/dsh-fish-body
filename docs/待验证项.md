## V1 TTS：桌宠知不知道自己的嗓子，能不能主动调用或唱歌

### 要验证什么

1. 宠物（对话 / 碎碎念用的那个 LLM）**是否知道自己有语音能力、有没有 GSV 这个本地音色源**；
2. 它能不能**自行决定**调用 GSV 发声（而不只是被动地被渲染端念出来）；
3. 用户口头要求换嗓子（「用纳西妲的声音说这句」）时会发生什么。

### 当前代码事实

- **能力感知已接入**：`src/host/voice/capability.ts` 会把可用实现、当前音色、不可用原因和播报开关拼成稳定事实，
  由 `composeSystemPrompt` 放在名字之后、时间之前。数据与 `/voice/voices` 同源。
- **不能自行调用**。宿主侧没有把语音暴露成模型工具（`src/host/**` 里没有给 LLM 注册 tool 的地方）；
  发声是**渲染端**在拿到回复文本后自己发起的：`src/client/pet/card/*` 与 `src/client/chat/state.ts` 调
  `src/shared/voice.ts` 的 `playSayVoice` / `speakText` → `POST /voice/speak` → 宿主 `src/host/voice/chain.ts`。
- **嗓子是全局单例**。`shared/voice.ts` 的 `voiceName` 由 `setVoiceConfig(name)` 从设置里灌入，
  只有设置变更才更新；`/voice/speak` 的请求体只有 `{ text, voice? }`，**没有 provider 字段**，
  所以即使能调也只可能换音色，不能按句选「用 GSV 还是 edge」。
- **provider 选择在宿主回退链里**：可用免费第三方按注册顺序在前，内置 edge 收尾；
  按量计费的 cloud 只有用户显式开启时才作为链首，失败仍回落免费链。
- **TTS 只合成说话**：可以念歌词、带节奏朗读或利用 provider 的语气标签表演，但不会生成歌曲旋律。

### 判据

| 项 | 期望（当前实现） | 备注 |
| --- | --- | --- |
| GSV 起来后 `/voice/voices` 的 `gsv.available` | `true` | 这是链路可用性的唯一判据 |

| 口头要求换嗓子 | **音色不变** | 全局设置优先，per-message 无通道 |

### 结论（待填）

- [ ] GSV 可用态验证：_（未做，需要真实本地服务）_
- [x] 主动感知代码与单测：_（capability + persona 已覆盖）_
- [ ] 自行调用验证：_（预期失败——没有 tool 通道）_

### 如果不满足，改法方向

1. **让它能调用**：给 LLM 注册一个工具（如 `speak({text, voice})`），或在回复文本里支持一条 cue 语法
   （项目已有 cue 分发：`src/client/pet/card/cue-effects.ts` 的 `say` 指令）——后者更贴合现有架构，
   渲染端解析到 `say` 时带上 voice 覆盖，就能做到「这句话用这个嗓子」。
2. **要按句选 provider** 的话，得把 `/voice/speak` 的请求体扩成 `{text, voice?, provider?}`，
   并让 `voice/chain.ts` 接受「只看某一个 provider」的模式（现在是回退链，没有单点模式）。
3. **真正唱歌**是独立能力：需要歌声合成/SVC、音高与节拍轨道，不能复用普通 TTS 时假装完成。

### 已知风险

1. **卡很长时提示词会很长**：这张 12 KB 的卡投影出 **1,781 字**系统提示词，碎碎念这种短任务也带着它。
   本次对话 1.5 s / 碎碎念 0.6 s（本机模型快），**看不出压力**——换慢模型或长卡（10 K+ 字）要重新量。
   若出现「碎碎念变慢/变贵」，先量这段。
2. **`system_prompt` / `post_history_instructions` 原样进正文**：卡里如果写了「你必须用 JSON 回复」这类
   指令，会直接落到系统提示词里——这是设计使然（尊重卡作者），但要验证它不会破坏气泡的纯文本假设。
   本次这张卡的 `post_history_instructions` 是 285 字的说话风格约束，落在正文末尾，**没破坏纯文本**；`system_prompt` 为空，**该路径仍未覆盖**。
3. **`mes_example` 占正文 32%（577 / 1,781 字），里面带 `<START>` 与「主人: / 鱼生:」逐轮格式**。
   本次两轮生成都没照抄（没有前缀、没有 `<START>`、没复述开场白），但这是「这次没犯」——
   换弱模型或把示例写得更像模板时风险仍在。要彻底降风险，只能改投影策略（示例只留片段，或改成非对话式描述）。
4. **同名角色覆盖**：`POST /persona/scan` 返回里有 `reused` 字段（本次 `false`），说明重复导入走复用而不是复制；
   但「两张同名不同内容的卡」会怎么落盘还没撞过。
5. **PNG 卡**：`tEXt` 解析路径本机没有样本可测（`fish-soul` 是 JSON 卡），暂记为未覆盖。
6. **还原要连运行期一起还**：`apply` 改的是配置文件，但实例内存里还留着旧的那份；只还原文件不重启，
   会出现「盘上是旧人设、宠物还按新人设说话」。本次还原后重启了 3099，`/persona/characters` 随配置一起回到 `[]`。

## V3 soul 类项目兼容矩阵 + 作息同步（⚠️ 兼容面已扩到 Markdown，作息仍不可靠）

### 要验证什么

用户定的分工是「**soul 是灵魂，本项目是身体**」：装一个 soul 类项目 + 本项目之后，
人设与行为该由 soul 侧定义、本项目只负责长相与动作。这条要验三件事：

1. 注册在册的四个 soul 来源（`fish-soul` / `dsh-soul` / `dsh-rofm` / `dsh-suzu-memory`）**认不认得出各自的产物**；
2. 认出来之后，**换灵魂身体会不会跟着变**（同一只宠物、同一套渲染与动画，只换人设）；
3. soul 侧定义的**作息**能不能同步——宠物会不会按当前时刻判断「该不该困、该不该催睡」。

> **2026-11-25 晚更新**：第 1 条原本只支持 SillyTavern v2 卡，Markdown 那两家（`dsh-soul` / `dsh-soul-md`）
> 一个都读不到。现已补上**通用 Markdown 解析器**（见本节末「追加实现」），兼容面从 1/4 扩到 3/4。

### 当前代码事实

- 扫卡规则只有一份，在 `src/host/persona-source/card-file.ts`，认三种布局：
  1. `<目录>/persona.json`（单卡，SillyTavern v2，含 PNG 卡的 `tEXt chara`）；
  2. `<目录>/personas/*.{json,png,md}`（一文件一角色）；
  3. `<目录>/*.md`（Markdown 人格文档族：一份 = 单角色，多份 = **合并成一个角色**；有 `persona.json` 时不看顶层 md）。
     单卡上限 1 MiB；`README` / `LICENSE` / `CHANGELOG` 那类项目文档不算人格。
- Markdown 的语义按**文件名**定（`SOUL.md` 人设 / `IDENTITY.md` 身份 / `STYLE.md` 说话风格 /
  `AGENTS.md` 规则 / `HEARTBEAT.md` 作息与节律 / `USER.md` 关于主人 / `MEMORY.md` 长期记忆），
  顺序固定、第一段不戴标签；名字按「显式声明（`名字：X` / `名字是「X」` / `Name: X`）→ 一级标题 → 文件名」推断。
  实现见 `src/host/persona-source/markdown-card.ts`。
- 卡片解码 `card-reader.ts` 仍**只认 v2**，只投影 8 个字段；`extensions`、`character_book`、
  `tags`、`alternate_greetings`、`creator_notes` 一律丢弃。
- **本项目没有任何「作息」概念**：除 `POST /sleep` / `POST /wake`（手动让它睡/醒）之外，
  没有时刻表、没有按点触发、没有时段规则。
- 时间背景由 `time-context/context.ts` 的 `timeContextOf()` 拼进 system **末段**，形如
  `【当下】现在是2026年11月25日星期三 13:13，下午，工作日。这只是背景，不必刻意报时，也别句句都提节日——多数时候正常说话就好，真贴切时才顺口带一句。`
