# 计划编制规范

这份文档解决什么问题：多任务计划写错依赖边，图就会成环，而且环上每条边单看都「理由充分」，静态读一遍很难发现。等实施阶段才撞上时，代价是「实施顺序被迫自定、上游设计与实施永久不一致、评审只能靠实施方自述去对照」。本文给出四条机械约束与一段找环脚本，把这件事从「靠自觉」变成「跑一下」。

---

## 依赖边写产出物，不写消费者

依赖边声明的是「我要的那件东西**现在还不存在**」，不是「那件东西还有谁在用」。

| 写法 | 语义 | 结果 |
| --- | --- | --- |
| `依赖：T-B` | 依赖另一个**任务** | B 只要复用了我产出的东西，边就立刻成环 |
| `依赖：ui.ts::pair（由 T-A 产出）` | 依赖一件**产出物** | 指向明确，可排序；产出者唯一 |

典型踩坑模型：`pair`（两列布局小件）与 `tree-row`（行渲染小件）是两个**新建**的小件，A 先造出来，B、C、D 都复用。

- 错误写法：B 依赖「要用 `pair` 的那个任务」、D 依赖 B、C 依赖 B 与 D → A ↔ B ↔ D 成环。
- 正确写法：A 依赖「无（新建）」；B 依赖 `ui.ts::pair（由 T-A 产出）`；C 依赖 `tree-row` 的抽取位置（由 T-B 产出）；D 依赖 `T-B 产出的插槽`。四条边全部指向产出物，图是一棵树。

判据一句话：**如果两条任务共用一件还不存在的东西，就把它显式列成一条产出任务，其余任务依赖它，而不是互相依赖。**

## 编号即拓扑序

一条最便宜、且能挡住绝大多数环的机械约束：

> 所有被依赖项的编号，必须**小于**自身编号。

它把「图是否可排序」降级成「一眼能不能看出来」。真出现「A 依赖 B、B 的编号却更大」时，无需论证，**说明编号该重排**，而不是图该特批。

| 检查 | 成本 | 抓什么 |
| --- | --- | --- |
| 编号单调 | 数一下就完 | 绝大多数环、以及「先删后建」的反向顺序 |
| 找环脚本 | 一条命令 | 编号被重排后重新引入的环 |

编号顺序与「叙事顺序」不一致是正常的：计划的章节顺序按功能讲，编号顺序按**谁能先造出被复用的东西**排。两者冲突时改编号，别改依赖。

## 单写者规则

同一文件被多个任务改时，必须指定唯一写者：

| 任务 | 对同一文件的角色 | 能否出现在别人的依赖边里 |
| --- | --- | --- |
| 单写者（writer） | 唯一允许改盘的那个 | 能 |
| 只读消费者（read-only consumer） | 只读、只调用，不改 | 不能 |

只读消费者之间**天然无依赖**——它们都只依赖「写者产出的那个形状」。把消费者之间连边，是成环的第二大来源。

做法：在计划里给每个任务加一行显式角色标注（`writer: ui.ts` / `consumer: ui.ts`），评审只看 writer 行是否唯一。

## 定稿前跑一次找环

十行脚本，不依赖任何工具链。约定：每个任务是一节，标题形如 `### T-A 标题`，节内有一行 `依赖：T-B, ui.ts::pair`。

把下面这段存成 `scripts/check-plan-cycles.mjs`：

```js
// scripts/check-plan-cycles.mjs — 解析计划里的「依赖：」行并找环；有环 exit 1
import { readFileSync } from 'node:fs';

const text = readFileSync(process.argv[2], 'utf8');
const edges = new Map();
let current = null;
for (const line of text.split(/\r?\n/)) {
  const head = line.match(/^#+\s+(T-[A-Z0-9]+)\b/);
  if (head) { current = head[1]; edges.set(current, new Set()); continue; }
  const dep = current && line.match(/^\s*[-*]?\s*依赖[:：]\s*(.+)$/);
  if (!dep) continue;
  for (const id of dep[1].match(/T-[A-Z0-9]+/g) ?? []) edges.get(current).add(id);
}

const state = new Map(), stack = [], cycles = [];
const walk = (id) => {
  const s = state.get(id) ?? 0;
  if (s === 1) return cycles.push([...stack.slice(stack.indexOf(id)), id].join(' -> '));
  if (s === 2) return;
  state.set(id, 1); stack.push(id);
  for (const next of edges.get(id) ?? []) walk(next);
  stack.pop(); state.set(id, 2);
};
for (const id of edges.keys()) walk(id);

if (cycles.length) { console.error(cycles.join('\n')); process.exit(1); }
console.log(`ok: ${edges.size} 个任务无环`);
```

用法（计划目录用占位）：

```bash
node scripts/check-plan-cycles.mjs <计划文件>
```

它只做一件事：有环就 `exit 1` 并打印环上的任务序列。**把它挂进计划定稿前的最后一步**，而不是事后补。

## 已经发现环了怎么办

已经写进计划、评审也过了，实施阶段才发现成环——按下面四步处置，不要暗改上游。

1. **不改上游产物**。设计/计划文档不归实施阶段改；错误要留成证据，改掉就没人能复核了。
2. **在实施报告里单独立节**，写清三件事：环在哪几行依赖、实际按什么拓扑序落地、每个任务的真实落地顺序。标题里点名「评审请对照」，让评审一眼抓到上游与实施的不一致。
3. **把环的代价记账**。例如「先删后建」造成的能力空窗：某个开关先被删掉、真正替代它的任务排在后面，中间这段时间只能靠配置文件改。代价必须被看见，藏起来等于让下一个读计划的人再踩一次。
4. **例外由协调者裁定**，实施方不自行重排计划来「让图好看」。下一轮把编号按真实拓扑序重排，别把例外留成惯例。

两条反向提醒（别为了消环而过度串行）：

- 共享的是**纯类型、常量、文案键**（无行为、无装配顺序）时**不构成真依赖**，不要建边，否则会造出假环，白付串行化的代价。
- 若两条任务确实互不可分（同一组件的结构必须一次定形），正确动作是**合并成一条任务**，不是编两个编号再互相依赖。
