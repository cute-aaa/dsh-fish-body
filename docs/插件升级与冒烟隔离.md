# 插件升级与冒烟隔离

这份文档解决什么问题：两件「看起来已经隔离了」的事，其实都没隔离。其一，起一个临时 profile 做冒烟，直觉上配置已隔离，实际每一次写盘都落进用户真实的插件数据根。其二，给配置新增一个实例字段，新构建写得很成功，另一个仍在运行的旧实例随手保存一次，这个字段就无声消失。前者会污染用户环境，后者会丢用户配置；两者都不会让本地门禁变红。本文给出这两条链路的解析规则、可粘贴的快照/还原命令与一套部署顺序。

---

## profile 隔代码，DSH_HOME 管数据

两层根不是一回事，混起来就会得出错误结论：

| 层 | 由什么决定 | 换 profile 会变吗 |
| --- | --- | --- |
| 宿主 profile 目录 | `join(DSH_HOME, profiles, <name>)` | 会 |
| 插件数据根 | 在 `DSH_HOME` 下解析（见下节） | **不会** |

结论一句话：`--profile` 隔离的是**插件构建与宿主配置**，不是**插件数据**。数据根挂在 `DSH_HOME` 上，而 `DSH_HOME` 本身没有 profile 分量（默认 `~/.dsh`，或被环境变量改写）。

所以「起了临时 profile + 把工作树 junction 进去」这种冒烟姿势，只能保证跑的是哪份代码，不能保证写到哪份数据。判据也很简单：**冒烟前后要不要手工复原用户的文件**——要，就没有隔离。

## 数据根解析顺序

`dsh-fish-body/src/host/locations.ts` 的 `resolveRootDir` 按优先级取第一个可用值：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 `DSH_PET_USER_ROOT` | 指向哪个目录就用哪个；冒烟想要真隔离就靠它 |
| 2 | 指针文件 `<DSH_HOME>/fish-body-root.json` | 内容是另一个目录的路径；**被改也会换根** |
| 3 | 默认 `<DSH_HOME>/fish-body` | 前两者都没有时 |

两个容易漏的细节：

- 指针指向的目录**不存在**时不硬用它，而是回落默认根并记一条 warn——否则「换盘后没挂载」会变成一次空数据启动。
- 数据根不止一个目录：指针文件本身在 `<DSH_HOME>` 下、运行时（`<数据根>/runtime/electron`）也在同一面上。冒烟若会拉运行时，快照范围要一并覆盖。

冒烟抬头第一句先写清实际值，别靠记忆：

```powershell
Write-Output "DSH_HOME           = $env:DSH_HOME"
Write-Output "DSH_PET_USER_ROOT  = $env:DSH_PET_USER_ROOT"
Get-Content "<DSH_HOME>\fish-body-root.json" -ErrorAction SilentlyContinue
```

## 冒烟前的快照

**首选：让数据根彻底离开用户目录。** 环境变量优先级最高，把根指到临时目录即可，跑完直接删目录，不需要还原：

```powershell
$env:DSH_PET_USER_ROOT = Join-Path $env:TEMP ("fish-body-smoke-" + [guid]::NewGuid())
New-Item -ItemType Directory -Path $env:DSH_PET_USER_ROOT | Out-Null
```

**次选：改不了环境变量就快照。** 数据根与指针文件一起拍，两个都要：

```powershell
$snap = Join-Path $env:TEMP "fish-body-snap"
robocopy "<DSH_HOME>\fish-body" $snap /MIR
Copy-Item "<DSH_HOME>\fish-body-root.json" "$snap.pointer.json" -ErrorAction SilentlyContinue
if ($LASTEXITCODE -ge 8) { throw "快照失败，退出码 $LASTEXITCODE" }
```

`robocopy` 成功时的退出码是 **1–7，不是 0**；只有 `>= 8` 才算失败。所以别用 `if ($LASTEXITCODE -ne 0)` 判定，否则每次成功冒烟都会被脚本判成失败。

快照要**在冒烟进程启动之前**完成；冒烟过程中别再往里写东西。若冒烟会拉运行时（Electron），把 `<数据根>\runtime` 也列进同一份快照，别只拍 `config` 与 `data`。

## 冒烟后的还原与比对

```powershell
$snap = Join-Path $env:TEMP "fish-body-snap"   # 与快照时同一个值
robocopy $snap "<DSH_HOME>\fish-body" /MIR
if ($LASTEXITCODE -ge 8) { throw "还原失败，退出码 $LASTEXITCODE" }

# 指标一：主配置的 md5
(Get-FileHash "<DSH_HOME>\fish-body\config\main-config.jsonc" -Algorithm MD5).Hash

# 指标二：角色库的文件条目数（一角色一文件）
(Get-ChildItem "<DSH_HOME>\fish-body\data\persona-characters" -File).Count
```

**两项都回到原值才叫零残留。** 只比 md5 不够：角色库是「一角色一文件」，新增或删除角色文件根本不改主配置，md5 会一模一样地通过。反过来也是一样，只数条目会漏掉「配置里多了一个字段」。

报告里要写清**比了什么、没比什么**：截图、日志这类落在 `<数据根>` 之外（或压根不落盘）的宿主状态，不必强求一致，但必须明写「未纳入比对」，否则下一次没人知道这份「零残留」的边界在哪。

## 新增实例字段的升级顺序

前提认知：`pets[]` 是**整包白名单重建**——保存时按固定字段表新建对象，表里没有的键直接不写出。因此「加类型 + 加读侧默认值」不足以让字段存活。

1. **写侧先改齐**。新字段必须出现在 `dsh-fish-body/src/host/config/save.ts` 的 `pet = { … }` 字面量（以及配套的写回指纹）里，否则下一次保存就是一次合法的「删键」。
2. **部署顺序固定**：停旧实例（或合流后重启）→ 新构建接管 → 再让用户保存。中间态允许「旧构建仍在跑」时，任何一次保存都会丢新键。
3. **读侧宽松、写侧严格**。读侧遇到非法/缺失值告警并回落，写侧遇到非法值整包 `400`——别让用户手改一次就静默丢数据。
4. **顶层字段不同命**。非白名单的顶层键从 `existing` 原样透传保留，所以能活下来；只有 `pets[]` 内的实例字段受重建影响。判断某字段属于哪一类，就看它是否出现在那个 `pet` 字面量里。

这类问题只在「跨构建版本 + 旧实例仍活着」时出现，单机本地测试永远抓不到，只能靠真机或双构建对照。

## 运行代码对账三件套（`Target → 命令行 → 产物 md5`）

`npm run build` + 重启只说明**动作做了**，不说明**运行实例加载的是哪一份字节**。插件挂载是 junction，它完全可能指向另一个 checkout（历史上就出现过指向 `.agents/worktrees/*` 的情况），此时在主检出构建等于没构建。判「已生效」必须三件套齐全，全部只读：

```powershell
# ① 运行代码从哪来：Target 不是你以为的那份 → 后面一切真机结论作废
Get-Item $env:DSH_HOME\plugins\dsh-fish-body | Select-Object LinkType, Target
# ② 哪个进程在跑它：命令行要能对上 profile / 端口
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match '--port 3099' } | Select-Object ProcessId, CommandLine
# ③ 字节是否同一份（主检出 vs junction 目标）；不等＝少跑一次 build 或构建落在另一份检出
$MAIN   = 'G:\Projnew\ai\dsh-fish-body\dsh-pet'
$TARGET = (Get-Item $env:DSH_HOME\plugins\dsh-fish-body).Target
foreach ($f in 'lib/client.js','lib/app.js','lib/chat-panel.js','lib/standalone.js',
               'runtime/electron-helper/shared-core.js') {
  $a = (Get-FileHash (Join-Path $MAIN $f) -Algorithm MD5).Hash
  $b = (Get-FileHash (Join-Path $TARGET $f) -Algorithm MD5).Hash
  '{0} eq={1}' -f $f, ($a -eq $b)
}
```

判读顺序固定：① 定了路径 → ② 定了进程 → ③ 才谈字节。反过来先看 md5 会得出「两份一样」却不知道哪一份在跑。

发布前清单里建议保留第 ③ 步：只跑 `npm run build` 不核对 md5，等于把「产物是否落在运行份上」交给运气。

## 启动失败先看端口，别信「import failed」

`--port 3099` 上已有实例在跑时，再启动一个的报错长这样：

```
dsh: startup failed: 2 required plugins did not activate
Failed plugins (1):
  webserver (required)  Error: listen EADDRINUSE: address already in use 127.0.0.1:3099
Plugins waiting for services (6): … dsh-fish-body  Missing services: webServer
```

浏览器侧还会补一句 `dsh-fish-body: import failed (see console for the import error)`。**两句都不是插件的错**：webserver 抢不到端口 → 6 个依赖 `webServer` 服务的插件全部进入等待态 → 插件自身的 `apply` 压根没跑，客户端 entry 也就不会 activate。真实根因只在那行 `EADDRINUSE`。

判读顺序：

1. `netstat -ano | Select-String ":3099"` 看有没有 `LISTENING`；有就是重复启动，先停掉旧 PID 再启。
2. 确认旧实例是死是活：`Invoke-WebRequest http://127.0.0.1:3099/?token=<启动行 token>` 拿到 200 说明它健康，**不需要重启**——重启只会打断正在用的浏览器会话，而加载的仍是同一份字节。
3. 只想让插件代码生效（改了 `src/**` 并已 `npm run build`）：`POST /dsh-pet-7340/plugin-restart` 比重启整个 profile 更轻；要重载桌面 helper 用 `POST /dsh-pet-7340/desktop/stop` 再 `POST /dsh-pet-7340/reload`。

只有 `EADDRINUSE` 消失后仍报 `did not activate`，才轮到查插件本身。

## 旧构建认不认这个键：30 秒自检

升级前，直接问旧产物这个键名出现过几次：

```bash
# <构建产物> 本仓为 dsh-fish-body/lib/index.js；<新键名> 换成你要加的字段名
node -e "const fs=require('fs');const p='<构建产物>';const s=fs.readFileSync(p,'utf8');console.log('KEY',(s.match(/<新键名>/g)||[]).length,'mtime',fs.statSync(p).mtime.toISOString())"
```

判定很硬：

| 输出 | 含义 |
| --- | --- |
| `KEY 0` + 旧 `mtime` | 这个构建的**任意一次保存都会删掉该键**，必须先停它再上新构建 |
| 命中次数 > 0 | 该构建认识这个键，可并存；仍建议按上面的部署顺序走 |

**升级后还要反向验证一次**：新构建写一次 → 旧构建读一次（确认能读到）→ 旧构建保存一次 → 再确认键仍在。本仓可照搬的观测方式是「写入后取一次 md5，旧构建保存后再取一次」，两次一致才叫字段存活。

## 真实实例上的破坏性用例：快照、双判还原与 junction 代价

前两节讲的是「换根隔离」。当任务要求**必须测真实实例**（用户就是这么要求的）时，隔离手段换成「快照-还原」，判据也必须一起换。

**开跑前**
1. `robocopy "<数据根>" "%TEMP%\qa-snapshot-<ts>" /MIR`，退出码 **1–7 = 成功**、`>= 8` 才失败（用 `-ne 0` 判会把每次成功快照判成失败）。
2. 记四项基线：主配置 `md5`、`data/persona-characters` 条目数、`skin/<三种渲染方式>` 条目数、`skin/*-config.json` 清单；再加宿主 `webPid`（验证宿主实例全程没被换掉）。

**收工前**
3. 先杀本轮起的子进程（Electron/keeper/临时 cmd），再反向 `/MIR`。
4. 双判：**`Files.failed = 0`** 且 **四项与基线全等**。只对一项不算还原。
5. 还原后重启被测实例，让它加载还原后的配置，并重新取 token。

**junction 的代价（必须知道）**：`/MIR` 不保证还原**链接拓扑**——快照侧会把 junction 落成普通空目录。若数据根里本来有指向其他位置的 junction，快照只能保住内容，不能用来在新机器上重建链接。所以报告里只能写「文件 0 failed + 内容四项全等」，**不能**写「链接也还原了」。

## 证据链三方对账与 `partial-evidence`

测试结论的强度必须与证据强度匹配，而门禁只能证明代码自洽。收工前把三处对一遍：

| 对账项 | 怎么判 |
| --- | --- |
| 摘要计数 = `cases/` 文件覆盖的用例数 | 逐条列 ID，缺一条就说明为什么 |
| 摘要结论 = 该用例自己的结果文件 | 例如结果 JSON 里 `passed:false` 就不能在摘要里记 passed |
| 用例文档正文 = 它引用的日志 | 常见矛盾：正文写「0→0」而日志是 `1→1` |

- 没有独立证据文件的用例标 `partial-evidence` 并指向聚合文件与具体小节，不要含糊地记 passed；
- 顺序纪律：**先跑 → 落盘日志 → 写用例 → 最后写摘要**；反过来写必然漂移。
- 结果文件里的措辞也要对齐契约（例：条目名叫「4xx」而实际 `status=200`，会让下一个人按 4xx 写断言）。
